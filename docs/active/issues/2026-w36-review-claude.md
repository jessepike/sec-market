I reviewed the diff (`git diff preview...weekly-issue`, 35 files) against `weekly-issue-spec.md` v0.2, `gather-job-spec.md`/`gather-brief.md` v0.2, and `intent.md`. Findings below, most severe first; full writeup also saved to `/Users/jessepike/.claude/plans/you-are-reviewing-a-happy-castle.md`.

**1. Blocker — a published issue's posture-delta and thesis evidence ids are never resolved.** `web/scripts/verify-issue.ts`, check 4 (lines 198–218). Check 4 only validates `item.evidenceIds` on the four lane items. It never touches `weThink.postureDeltas[].evidenceIds` or `weThink.thesis.evidenceIds` (or `proposed.thesis.evidenceIds` on a draft). Check 12's numeric-token check touches those ids but silently skips an unresolved one (`if (!record) continue`) rather than failing, and no other check resolves them. So a signed, published issue can carry a nonexistent evidence id in its posture delta or its thesis score and pass all 11 gates — `WeThink.tsx` still renders an evidence-link button for it that resolves to nothing. This is exactly the "evidence id that does not resolve" scenario you asked me to test, and it gets through for the highest-stakes fields on the page rather than a lane item. To be fair to the implementation: `verify-issue.ts` matches spec §6 check 4 literally, which is itself scoped to `IssueItem.evidenceIds` only — this is as much a spec gap as a code gap. Smallest fix: extend check 4 to resolve `postureDeltas[].evidenceIds` and `thesis.evidenceIds` the same way item ids are resolved today.

**2. Should-fix — the vendor lens (SEC-031) isn't built.** `web/src/App.tsx` lines 51–52 leave a placeholder div with a comment marking it "task B4, not built here." Spec §9 lists "Vendor lens filters and is shareable by URL" as an acceptance condition and §7 requires `tests/e2e/lens.spec.ts`; neither exists in this diff. If this branch is meant to close out the spec, it doesn't meet its own acceptance bar. If it's an intentional split, that should be recorded as a decision somewhere rather than live only as a code comment.

**3. Should-fix — header nav is dead on the two new routes.** `web/src/components/Header.tsx` lines 11–19 and 83–96. The same nav renders on `/`, `/issues/`, and `/issues/<id>/`, but five of its seven items (Thesis, Landscape, Scorecard, Evidence, Method) are hash anchors to sections that only exist on the front page. On the other two routes, clicking them calls `preventDefault()` then silently no-ops.

**4. Nit — the `background` exemption doesn't check direction.** `web/scripts/verify-issue.ts` check 4, lines 210–214. `background: true` exempts an item from the window check entirely, but the spec's intent is specifically "dated before the window." An item dated *after* the window with `background: true` set would also pass silently. Smallest fix: require `item.date < start` when `background` is set.

**5. Nit — landscape cards now use a full sentence as their accessible heading.** `web/src/components/DomainBoard.tsx` lines 94 and 96. Per spec, the card's `<h2>` moved from the short domain name to a 2–3 sentence "trigger sentence," with the domain name demoted to a non-heading `<p>`. That's what the spec asked for, but it means a screen reader's heading-navigation list no longer surfaces the four domain names at all — worth flagging as a seen cost, not an oversight.

**6. Nit — no trailing-slash/404 handling for the new directory routes.** `web/vercel.json` is unchanged, but this diff is what first ships `/issues/<id>/`-style directory routes. There's no `trailingSlash`/`cleanUrls` setting and no custom 404 page, so a URL without the trailing slash is at the mercy of Vercel's default static resolution.

What held up well: the lock manifest is genuinely append-only (`--write` refuses to alter existing entries, and the gate independently re-hashes every entry every run); two drafts, a draft that isn't newest, publish-without-signer, a wrong signer, and a proposal left on a published issue are all correctly caught; routing/prerender/feed/sitemap are all driven generically off the `issues` array with nothing hardcoded to the single current draft; there's no SSR/hydration risk (no `window`/`document` access in the new components, identical trees in `entry-server.tsx` and `main.tsx`); the RSS feed is valid, excludes drafts, and its item count is independently cross-checked in `verify-dist.ts`; and the gather brief's field names, file paths, and npm script names all match what's actually in the code.

Verdict: merge after should-fixes. Finding 1 is cheap to close and guards the signed judgment itself, so I'd want it fixed before this becomes the pattern future weekly issues get drafted against. Findings 2 and 3 deserve an explicit decision rather than a silent gap, but neither corrupts data or breaks a route.
