The seven planned endpoints are additive to the current generic diagnostic fanout. The runtime probes all 25 candidate `official_discovery` rows first. Each can make one root request, one robots request, and up to eight advertised RSS/sitemap requests: a ceiling of 250 generic logical reservations. The explicit plan then attempts up to seven more, for a maximum of 257 logical reservations. Schema 1 has no switch to suppress the generic fanout. At the archived post-Orca budget count of 1,980/5,500, that ceiling would bring the count to 2,237, leaving 3,263. Logical reservations do not cap transport retries or redirects.

The explicit target loop follows the generic probes. A deadline or budget denial can therefore prevent a target from receiving an HTTP request. `_probe_qualification_targets` records a result row for each target in a returned report; denied rows stay incomplete, and the final source-probe guard marks the overall run denied if the last in-flight request crosses the deadline or UTC boundary. The preflight proves plan validity, not that all seven requests will complete. A failed or blocked target remains diagnostic evidence only; the operation grants no source, semantic, qualification, coverage, model, or publication credit.

The endpoint choices leave scope questions open by design. The LevelBlue feed still needs evidence that its items map to the Trustwave relationship; the Check Point feed is a broad parent blog rather than an Email Security-specific source; and PR Newswire responses must preserve Aqua as the issuer. The current proof supports selecting these candidate endpoints for diagnosis, not activating them. Their new responses would need actual body, date, issuer/scope, and pagination review.

I would keep the plan available as a bounded next diagnostic if the owner elects to use it.
