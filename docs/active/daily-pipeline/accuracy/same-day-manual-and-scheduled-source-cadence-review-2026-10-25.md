# Same-day manual collection and scheduled-source freshness

Yes. A manual collection and a later scheduled collection using the same contract on the same UTC day can reuse source work without renewing its original transport time. This is supported by current code and an actual earlier-policy scheduled run. If the next scheduled collection is delayed beyond the retained source deadline, the public release can become overdue before replacement. The ordinary new-UTC-day borrowing hypothesis remains disproved.

## Conditional timing and current recovery

The midnight-manual plus later-morning-schedule example is a supported risk, not an observed H sequence. If a source checked at 00:05 on one day is reused by that day's 09:34 scheduled run, it still expires at 06:05 the following day. Another next-day run starting around 09:34 would begin after expiry. Reuse reduces remaining freshness to 30 hours minus the source's existing age; a scheduled job's successful completion alone provides no new source clock.

The authenticated October 24 run began 4 hours 17 minutes 54 seconds after its 05:17 nominal timer. A 4-hour-37-minute delay would instead project a 09:54 start; that is a scenario, not that receipt or a guaranteed next run. The root reported recovery `40169973257` starting October 25 at 06:41 against frozen main `6d5e87fe`. If its earliest relevant new source check were 06:43, the arithmetic deadline would be October 26 12:43, later than a projected 09:54 start. This review has not examined that recovery's completed source/archive proof and assigns it no exact deadline or publication credit.

## Recommended future action

After the active recovery is verified, specify a distinct scheduled freshness cycle that performs genuine conditional checks for required source transport even when an earlier manual cycle succeeded on the same UTC day. Coordinate both task-receipt reuse and run-download replay; merely passing `force_refresh=True` is insufficient. Keep retry/resumption within that cycle, historical semantic reuse, original receipts and timestamps, current daily reservations and hard allowances intact. If an allowance prevents a check, retain the explicit gap rather than extending its clock. Add a bounded regression covering an early manual success, a later same-day scheduled cycle, and `force_refresh=True` with replay enabled.

This is a future design recommendation. It requests no schedule-frequency change, purchase, dispatch, allowance reset or active-recovery change. Main remains frozen.
